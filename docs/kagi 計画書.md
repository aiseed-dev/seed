書いた日: 2026-11-06。作者「それぞれのシステムの計画書、設計書、マニュアル、実際のシステムをつくれ」。Fable が書いた。作者が確定するまで案。

## 1. 一行

**kagi — 自分の秘密がどこにあるかを分かっていて、口と記録を機械で確かめる道具。** 鍵の値は一度も読まない。

## 2. 誰のために、何を守るために

業務システムを守る係のため。小さな会社で、ファイル共有とサーバーと VPN 機器を業者に預けてきた一人（`docs/鍵の管理の仕組み.md` §5c の会社）。守るのは、記録と鍵。警察庁の令和 7 年上半期の情勢では、ランサムウェアの被害 116 件のうち中小企業 77 件、侵入は VPN とリモートデスクトップの機器からが 8 割以上、原因は安易な ID・パスワードと、管理されずに残っていた不要なアカウント。kagi が当たるのは、この「どこに何があるか分かっていない」所。

## 4. 何をするか（鍵の管理の仕組み §5 の歩 1〜4 の、AI がやる列）

| 歩 | kagi がやる | 人が確かめる |
|---|---|---|
| 1 在庫表（K-14、K-04、K-05） | 在庫表の雛形。期限切れと期限の近い物の一覧。欄の抜け | 表に無い秘密が無い |
| 1 走査（K-13、K-14） | 指定した場所の中で秘密らしい文字列の在り処を報告する（場所と種類だけ。値は出さない） | 報告の場所の物が在庫表にあるか、消すべき物か |
| 3 口（K-07） | 機械の口の一覧（`ss -ltnp` の出力）と口の表を突き合わせ、表に無い口と、表にあって開いていない口を出す | 一覧が表と一致 |
| 4 記録（K-06） | 追記だけの記録。連番とハッシュの連鎖と署名。検証 | 検証が通る。一行消すと落ちる |
| 機械（K-07、K-11、K-12） | Linux の機械を入れる時の答えの文と手順を書く。機械の写しを取り、機械の表・口の表・在庫表と突き合わせ、直す手を文で出す（設計書 §3.4） | 手順の通りに入れて、「直す物は無い」まで |
| 認証と鍵（K-12、K-14、K-05） | 誰が入れるか（アカウント、sudo、ssh の形）と、どの鍵で入るか（公開鍵の指紋、機械の鍵の指紋）を一つの表で見る。表に無い鍵・人・管理者を出す | 表に無い物が機械に無い |
| まとめ | 一枚の報告（人が読む物） | 読んで、次の歩へ |

歩 2（置き場）、5（控え）、6（根と二人）、7（発行者の機械）は人の手と機械の事なので、kagi は手順の文面だけ（手引き）。

## 5. 決まり

- 鍵の値を読まない。走査は「らしい文字列がある場所」だけを出す。在庫表に値の欄は無い。
- 外に繋がない。標準ライブラリだけ。網も API も使わない。例外は一つ: 人が打った時だけ、人の ssh と鍵で、読むだけの決まった文を機械で走らせて写しを取る（設計書 §3.4）。
- 機械を変えない。直す手と入れる時のファイルは文で出し、走らせるのは人。
- 記録は追記だけ。消す手は無い。
- 文書は素の文字（TOML、JSONL、Markdown）。kagi が無くても読める。
- 署名の鍵は人が置く（環境変数のパスか systemd の credential）。kagi はその鍵で署名するが出さない。

## 6. 何の事実で決まるか

1. seed の repo に置くか、digitaldoor に移すか。事実: 作者は層 2 の設計書を後で digitaldoor に移すと言った。kagi も同じ扱いでよい（独立したパッケージにしてある）。
2. 口の一覧を kagi が自分で取るか、人が貼るか。事実: `ss` を走らせるには機械に入る必要があり、AI の token の範囲（K-12）が決まっていない。最初は人が出力を貼る（ファイルで渡す）。
3. 走査の型の一覧。事実: 偽陽性が多いと人が読まなくなる。最初は型を少なく（鍵の頭の決まった形、PEM の頭、`password=` の類）。

## 9. aiai-tools との繋ぎ（11-06、作者「/aiai-tools にある ERP システムとの連携もできるのでは」。Fable が aiai-tools を読んで書いた。読むだけで、aiai-tools は変えていない）

aiai-tools（`/home/dev/dev/aiai-tools`。会社が外に預けている物を OSS と AI で自分の側に置くためのスキル集）には、kagi と隣り合う物が四つある。

| aiai-tools の物 | 何か | kagi との繋ぎ |
|---|---|---|
| `ninshou`（認証を PocketBase に集める。社員は Apple ID か Google ID） | 「管理できる人がいるか」の手順 1〜2 で、管理者の ID（ドメイン、DNS、サーバーの root と SSH、PocketBase の superuser、Forgejo、Apple と Google の開発者、ルーター、控えの置き場）を、何の管理者か・誰が持つか・二要素があるか・最後に確かめた日、で書き出す。パスワードと鍵は書かない。辞めた人や業者だけが持つ物を会社に伝える | **これは kagi の在庫表そのもの。** `inventory.toml` の `[[secret]]` の欄（id、kind、where、holder、role、expires、rotate_days）と同じ物で、ninshou は Markdown を会社のリポジトリ（`code`、Forgejo）に置くと言い、kagi は TOML で同じ場所に置ける。`kagi check inventory` が ninshou の「点検する」の道具になる。ninshou に無くて kagi にある物は、期限と回す周期の報告、走査、記録の連鎖 |
| `tenken`（ネットワーク機器の毎日の点検。公表された弱点と自分の機器の一覧を突き合わせて知らせる） | ルーター、VPN 機器、スイッチの弱点の知らせ | kagi が持たない所。警察庁の「VPN 機器の 48% がパッチ未適用」に当たるのは tenken。kagi は在庫と口、tenken は機器の弱点、で隣り合う。kagi の `ports.toml` の `host` と tenken の機器の一覧は同じ名で揃える |
| `kagi`（スマートロックの鍵を出す。民泊や事務所の扉に、本人確認の済んだ人へ期間付きの暗証番号） | 扉の鍵（Matter、RemoteLOCK、SwitchBot、igloohome、SESAME。Aliro 1.0 を見ている） | **名が同じ。** aiai-tools の kagi は扉の鍵を出す側（digitaldoor の層 1〜2 に近い）、seed の kagi は秘密の在庫と口と記録の側。中身は別で重ならないが、名が重なる。今は変えない（作者 11-06「変える必要はあるか」→ 無い）。理由: aiai-tools の kagi はスキルの文書で、`kagi` という命令も Python のパッケージも無い。seed の kagi は命令とパッケージ。同じ環境にぶつかる物が無い。変える必要が出るのは、二つが一つのリポジトリか一つの Python の環境に入る時か、aiai-tools の側に `kagi` の命令ができた時。その時は seed の側を `daicho`（台帳）にする |
| `tryton`（ERP。Tryton 8.0 LTS、PostgreSQL、`trytond` は `localhost:8000`、Web の画面 sao、admin のパスワードは人が端末で打つ。日本語と日本の会計は別モジュール `aiai_ja`） | 売る・買う・在庫・会計・人を一つのデータベースで。モデルも権限も全部ファイル（Python と XML）に書かれる | 下に |

**ERP（Tryton）との繋ぎ。** 鍵の管理の形（§5c〜5d）で言えば、ERP は「仕事ごとの口」の一番分かりやすい例で、四つの繋ぎがある。

1. **口。** `trytond` は `localhost:8000` に聞くので、`ports.toml` に `host = "erp", port = 8000, bind = "127.0.0.1"` と書き、外から見えるのは前に置いた門（パスキーで入る逆向きの代理）だけにする（§5d の形 1。ERP は触らない）。画面 sao は Web なので、社員は電話からでも入れる。業務だけ Windows が要る理由が ERP には無い。
2. **在庫表。** Tryton の秘密を `[[secret]]` に: PostgreSQL のパスワード（置き場 `erp:~/apps/tryton/…`）、`admin`、`trytond.conf` の session の鍵、控えの資格情報、門の鍵。値は書かない。
3. **記録。** Tryton の管理者の操作（admin のパスワードを替えた、モジュールを足した、権限を変えた）は、その時に `kagi log add --action erp.admin` を一行。Tryton 自身の帳簿（確定した書類は書き換えず打ち消しで直す）と、kagi の記録（追記だけ）は同じ形で、繋ぐ必要は無く、並べて置く。
4. **認証。** Tryton は自分の認証を持ち、PocketBase は他の道具にサインインを貸す側（OpenID Connect の提供者）にならない（ninshou が 2026-09-28 に確かめた）。だから門のパスキーと Tryton の ID の二段になる。一段にしたいなら、ninshou が挙げる Forgejo の OIDC か、Tryton の側の認証の差し替えで、どちらも aiai-tools の側の決め。

**seed との繋ぎ（設計だけ、今は無い）。** 基本計画 §1 の「自給の次」（売る、加工、宿や教室）の貨幣の記録は ERP の側にある物で、seed は畑の側の記録。二つを繋ぐ物は「場所と年のロット」（基本計画 §6 の種のロット ↔ Tryton の在庫のロット `stock_lot`）。畑で採れた物のロットが ERP の在庫になり、売った記録がロットに付く。作るなら Tryton の別モジュール（aiai-tools の決まり「本体に手を入れず別のモジュールに」）で、seed の公開の記録の URL をロットに持たせる形。作るのは 11-08 の後。

**同じ事を言っている所。** aiai-tools の README「企業の基幹システムは AI で扱いやすい。仕事の決まりがはっきりしていて、データも表の形にそろっている」は、基本計画 §1 の「欄のある所では AI が一日でシステムを作る」と同じ文。aiai-tools の「もう、コードは要らない時代」と、基本計画 §1 の「委託先に残る物は無い」も同じ。違う所は、aiai-tools が会社の側だけを書き、seed が畑の側（欄の無い所）を持っている事。

## 10. Linux の機械を入れる、動かす（11-06 夜。作者の言葉から）

作者: 「halo の設定は、あとにしよう。というか、Linux マシンのインストールや管理ができるようにして」「Linux マシンのインストールや運用は難しかったけど、AI 時代には逆に簡単になる」「特に認証はちゃんとやりましょう。そして、キーの管理もやりましょう」「この二つはセットでも問題ないはず」。

- **なぜ kagi に置くか。** `docs/鍵の管理の仕組み.md` §5c〜5e の会社（Windows と Samba を業者に預けてきた所）が Linux に移れない理由は、入れる事と動かす事が難しかったから。そこが簡単になれば、認証を一律に外へ預ける理由（§0b）が一つ減る。halo の門の設定はその一例で、先に道具を作る。
- **何が簡単になるか。** 人は表を書く（機械、役、入れてよい人、入れてよい鍵）。入れる時の答えの文、機械の今の形と表の差、直す手の文は道具が書く。覚える事が、表の欄の数まで減る。
- **人に残す事（簡単にしない所）。** パスワードを打つ、盤を選ぶ、機械の鍵の指紋を目で比べる、直す手を読んで打つ。ここを道具に渡すと、認証の根が道具に移る。
- **認証と鍵はひと組。** 誰が入れるか（アカウント、sudo、ssh の形）と、どの鍵で入るか（公開鍵、機械の鍵）は、同じ表（`machines.toml`）に並べ、同じ突き合わせで見る。鍵の期限と回す周期は在庫表（同じ id）。
- **halo。** 門（`deploy/halo/`）を当てるのは後。11-06 夜に作者「halo でやれ」: 作者の作業の場所 `~/farm/kagi/`（repo の外。番地と指紋とアカウントの名が入るため）に halo・deb2・机の PC の三台を書き、halo には dev の鍵で入って写しを取った。出た差は、口の門がまだ（11434・11435 が外向き、8080 が表に無い）、自動の更新が無い、dev に表に無い鍵が一本。ssh は鍵でだけ入る形で、防火壁は動いていた。直すのは作者（sudo）。
- **なぜ seed に要るか（作者、同じ夜）。** 「linux の管理ができなければ、自然農法のアプリを動かすときに Claude に聞かないといけない」「seed アプリでは、2 つのアプリがセット」「seed アプリでも、サイバー攻撃対策をしようと思ったら、何台かの PC が必要になる」「アプリの運用のためには、鍵管理は必須では」「鍵管理を避けるからアプリがおかしくなる」。畑のアプリを人に使ってもらう形で動かす人は、入口・本体・机と何台かの機械を持つ事になる。その人が機械の今の形を自分で見られ、止まったサービスの直す手を自分で読めれば、AI に聞くのは分からない時だけになる。だから機械の表に「動いているべきサービス」も書く。
- **機械ごとの役（作者、同じ夜）。** 「deb2 は、公開用。でも特定の人しかアクセス出来ないようにしようと思ったら認証システムは必須」「halo は、データベース用。文字データでないデータの場合は容量が大きくなるし、管理が難しい」「もう一台 miniPC があります。それを個人情報データ用にしますか？」。役ごとに機械を分ける（`docs/鍵の管理の仕組み.md` §3）と、機械ごとに見る物が違う: 公開の deb2 は入口の表（誰が、何で守られて入るか）、重いデータの halo はデータの置き場の大きさと盤の残り、個人情報の機械は盤の暗号化と、外からの入口が無い事。`deploy/deb2/` に deb2 用の表と手順を置いた。
- **手元の機械でやる理由（作者、同じ夜）。** 「AI を有効に活用しようと思ったら、クラウドなんか使っていられない」。AI に機械を見させ、直す手を書かせるには、機械の中身（設定、口、鍵の表、記録）を AI の届く所に置く事になる。借り物の機械ではそこが見えず、預けた認証（§0b の Entra）は自分で直せない。手元の機械なら、表も写しも素の文字で自分の側にあり、AI に渡す物を自分で選べる。今の外れ: seed の読みは Claude（外のサービス）を呼び、deb2 の前には Cloudflare が居る。線は「データと鍵と機械は手元、AI は呼ぶだけで、渡す物を選ぶ」。halo で動く手元のモデル（Glimmer）はその先。
- **表と裏（作者、同じ夜）。** 「『seed — Claude と一緒に種を播く』その裏側としてのセキュリティ対策用ツール」「seed は、自然農法を始める人のためのアプリ。でも、これを安全に動かすためには、裏で多くのことをしないといけない。こちらもできるだけ AI にさせないと回らない」「販売になると更に関係者が増えます。認証は大切です」「できるだけやりましょう。これが、サイバー攻撃対策ですね」。裏の仕事は、機械の形、鍵、入口、相手ごとの token、記録。同じ夜に seed のサーバーに門（相手ごとの token と記録。seed の設計書 §5.9）を入れ、kagi に `check tokens` を足した。
- **ルーターの検討（作者、同じ夜）。** 「追加でルータも必要でしょう」「配線図も書け」「ルーターに何をさせるつもりか。これは、個人の意見ではなくて、客観的に見るべきものです。調べて、必要かどうか検討しろ」。三台から実際に届くかを測り、NIST と警察庁と機種の資料を調べた。deb2 から届いたのは halo の 11435 とルーターの管理の口の二つだけ。今のルーターは RTX830 で、網を分ける事（LAN 分割）、管理の口を絞る事、通す物を決める事を持っている。追加のルーターは要らない。測った事、調べた事、検討は `docs/kagi 配線図.md`。
- **連載との関係（作者、同じ夜）。** 「ここと関係してきます。 https://aiseed.dev/debian-server/ 」「どうやってまもるか、ビルダーは協力すべきですね」。作者の連載「Claude と一緒に育てる Debian サーバー」が、人が一台を作って育てる手順。kagi はその良い形を、何台でも同じ見方で確かめる側。良い形の出どころは連載に置く（設計書 §3.4b の対応表）。守り方は一人ずつ考えるより、形を公開して並べる方が早い: 連載は誰でも読め、kagi は AGPL で、表と写しは素の文字。出し合えるのは「何を見るか」と「直す手」で、値と番地は出さない（表と写しは repo の外）。作者の三台も、出る向きの防火壁が連載の形と違っていた。自分の書いた形に自分の機械が合っているかは、道具で見て初めて分かった。
- **Flet で使える形（作者「linux の管理のためのツールをつくって、flet で使えるようにしろ」）。** `kagi app` を三つの画面にした: 機械（選ぶ、写しを取る、直す物と手、足す）、鍵（一覧、足す）、在庫・口・記録。
- **確かめていない物**は設計書 §3.4 の末尾。入れるファイルは本物のインストーラーでまだ通していない。
