## 0c. 標準の部分と、現場の部分（作者 11-06 未明「層 2 の設計書も標準的なものは AI が自動化できますね。でも、現場にあわせるのに人間が必要です」）

この文書を二つに分けて読む。**標準の部分**は、どの組織でも同じ形で、AI が書き、AI が保てる（認証局の骨格、鍵の階層、追記の記録、失効の配布、復元）。**現場の部分**は、その組織に行かないと決まらず、人が出し、人が確かめる（11-05 夕方の作者の言葉「現地に行って、その会社に合ったものにしない限り無理。それだったら、その会社の人が自分でやった方がいい」。基本計画 §1）。

| 標準（AI が書き、保てる） | 現場（人が出し、確かめる） |
|---|---|
| §1 役の六つと、できる事の分け方 | 誰がどの役か。一人が兼ねる時の切り替え方。二人の「もう一人」は誰か（§9 の 5） |
| §2 物の七つ（主体、扉と群、権限、資格情報、失効、記録、手順） | 扉の群の分け方、権限の中身（誰がどこへ、何時から何時まで）、出来事の手順の文面 |
| §3 鍵の五つ＋台帳の記録の鍵と、なくした・漏れた・替わる時の順 | 鍵を置く金庫と紙の場所、SE/HSM に何を使うか（§9） |
| §4 機械の役ごとの分離（R-AC-13）と口の最小 | 機械の台数、置く部屋、網の形、管理の画面をどこで動かすか（§9 の 3） |
| §5 出来事ごとの流れの 11 | 入社・退職の実際の手順（人事の流れとの繋ぎ）、本人確認の方法、網が届かない時間（R-AC-14 の最長の時間。§9 の 2） |
| §6 Wallet を発行者の一つとする形（R-AC-18） | Wallet を入れるか、いつか、費用を誰が払うか（§9 の 4） |
| §7 顧客ごとの分離の決まり（R-AC-09） | 顧客ごとに機械を分けるか鍵だけ分けるか（枠と顧客の数） |
| `audit.py` の形、SQLite の台帳、失効の配布の仕組み | 台帳を SQLite にするか（§9 の 1）、失効を押すか取りに来るか（§9 の 2） |

標準の部分は、この文書と `docs/鍵の管理の仕組み.md` を雛形に、組織ごとに AI が書き直せる。現場の部分は、§9 の「決めること」と上の右の欄で、人が現場で事実を見て埋める。digitaldoor の「運営がやってみせ、各社は雛形を参考に自分で作る」（R-RS-17）は、左を雛形、右を各社の人が埋める、という分け方そのもの。

## 1. 役（人）と、この層でできる事

| 役 | 誰 | できる事 | 入り方（層 3） |
|---|---|---|---|
| 管理者 | 鍵の管理者（会社は情報システム部門、分譲は管理組合、民泊は経営者。5.2b） | 扉が信頼する発行者の一覧を変える（R-AC-12）。発行者の鍵を足す・外す。二人で（K-09） | パスキー＋管理者の鍵（根。網の外） |
| 名簿の係 | 人事、総務、オーナー | 主体（社員、住人、客）を足す・変える・外す。どの扉の群に入るかを決める。**署名はできない** | パスキー |
| 発行者（機械） | 発行者の機械 | 名簿の係が決めた事に、発行者の鍵で署名して資格情報を出す。失効の一覧を作り、扉へ配る | 機械。人は入らない |
| 運用 | 機械を動かす人 | 機械の起動、控え、復元。**鍵は見ない** | ssh（鍵）、WireGuard |
| 監査 | 記録を読む人（管理者と別の人が望ましい） | 記録を読む。書けない | パスキー。読むだけの role |
| 本人 | 社員、住人、客 | 自分の資格情報を受け取る（カード、アプリ、Wallet）。自分の分の記録を見る | アプリのサインイン（パスキー）、入社時の本人確認 |

一人の人が複数の役を兼ねる組織（作者一人）では、役は分けたまま、同じ人が役を切り替えて入る。記録には役が残る。

## 2. 物（データ）

| 物 | 中身 | 誰が書く | 誰が読む |
|---|---|---|---|
| 主体 | 一人（または一つの機械）。呼び名、所属、状態（有効・停止・退出）、入った日・出た日 | 名簿の係 | 発行者、監査 |
| 扉と群 | 扉の一覧（扉の記録の公開鍵、据付の日）、扉の群（玄関、事務室、倉庫…）。扉が信頼する発行者の一覧（R-AC-12） | 管理者（信頼の一覧）、名簿の係（群） | 発行者、扉 |
| 権限 | 主体 × 扉の群 × 期間 × 曜日と時間 | 名簿の係 | 発行者 |
| 資格情報 | 発行者の署名付き: 主体、端末の公開鍵（5.2a）、届く扉の群、期限、役（住人・客・保守）。経路ごとに一つ（スマホの鍵、カード、暗証番号、Wallet、機械の鍵。R-AC-15） | 発行者（機械） | 扉、本人 |
| 失効の一覧 | 失効した資格情報の番号と日時。扉ごとに届ける分 | 発行者（機械） | 扉 |
| 記録 | 追記だけ。発行、失効、信頼の変更、人が入った事、復元。連番・ハッシュの連鎖・署名（`audit.py` の形を台帳側にも） | 全部の役（自分の行だけ） | 監査、管理者 |
| 出来事の手順 | 入社、異動、退職、紛失、端末替え、扉の故障、発行者の鍵の作り直し。紙にも（K-10） | 管理者 | 全員 |

台帳の置き場は発行者の機械の中（R-AC-19: 業者のクラウドに置かなくてよい）。seed の halo の PostgreSQL とは**別**（R-AC-13）。小さな組織なら SQLite 一つで足りる（主体は数十、扉は数個）。写しは控えの輪（K-08）。

## 3. 鍵（5.2b の五つが、この層のどこにあるか）

| 鍵 | 置き場 | この層での使い方 |
|---|---|---|
| 管理者の鍵 | 根。網の外（紙か金庫の USB。K-02）。二人（K-09） | 信頼の一覧の変更に署名（`trust-change`）。発行者の鍵の追加と削除。年に数回 |
| 発行者の鍵 | 発行者の機械の SE/HSM（R-AC-11）。無い間はファイル 600 ＋ systemd の credential（K-03） | 資格情報と失効の一覧に署名。日々。顧客ごとに別（R-AC-09） |
| 端末の鍵 | 本人の端末の保管庫（R-CM-16） | 公開鍵を資格情報に入れる。扉の問いかけへの署名は層 1 |
| 扉の記録の鍵 | 扉の SE（R-LG-04） | 公開鍵を台帳に写す。扉の記録の検証に使う |
| 台帳の記録の鍵（この層で足す物） | 発行者の機械の SE/HSM か、無い間はソフトの Ed25519 | 台帳の記録（§2）の署名。`audit.py` と同じ形 |
| 機械の鍵 | 発行者の機械 | 管理の画面との WireGuard か mTLS。Apple との mTLS（§6） |

鍵ごとの「なくした・漏れた・替わる」は 5.2b の二つ目の表のまま。

## 4. 機械

| 機械 | 役 | 口 | 盤 |
|---|---|---|---|
| 発行者の機械（別の PC。miniPC） | 台帳、発行、失効の配布、記録 | 入: 管理の画面からの WireGuard か mTLS だけ。出: 扉（ミニサーバー）へ失効の一覧と資格情報、Apple へ（§6）。**公開の Web は無し**（R-AC-13） | LUKS、TPM2 で自動解錠。発行者の鍵は SE/HSM |
| 管理の画面 | 管理者・名簿の係・監査が使う画面 | 発行者の機械へ WireGuard。画面は Flet（作者の意向。seed と同じ道具） | 管理者の PC |
| 扉（ミニサーバー、錠） | 層 1。信頼の一覧と失効の一覧と資格情報を受け取る | 発行者の機械から。網が無い時は最後に受け取った物で動く（R-AC-14） | 扉の SE |

| 控え | 台帳と記録の写し。三つの輪 | — | LUKS |

## 5. 流れ（出来事ごと）

1. **据付。** 管理者の鍵の公開鍵を扉へ（扉の前の物理の操作。R-AC-17）。扉の記録の公開鍵を台帳へ写す。記録に一行。
2. **発行者を足す。** 発行者の鍵を SE/HSM で作る → 管理者が信頼の一覧に足す署名（二人）→ 扉へ配る。記録に一行。
3. **入社（主体を足す）。** 名簿の係が主体と権限を書く → 本人確認（層 3）→ 本人の端末の公開鍵を受け取る → 発行者が資格情報に署名 → 経路ごとに配る（アプリ、カード、Wallet）。記録に一行ずつ。
4. **使う。** 層 1。扉が自分で確かめる（R-AC-10）。扉の記録は扉に残り、伝票として台帳へ上がる（R-CT-11〜17）。
5. **失効。** 退職・紛失・盗難: 名簿の係が主体を止める → 発行者が**その主体の全経路**を一度に失効（R-AC-15）→ 失効の一覧を扉へ配る → 網が無い扉は R-AC-14 の最長の時間で効く。記録に一行。
6. **端末替え。** 旧端末の経路を失効 → 新端末の公開鍵で出し直す。
7. **期限の更新。** 期限の前に自動で出し直す。期限の長さは R-AC-14 の最長の時間より短く（K-05）。
8. **発行者の鍵の作り直し**（漏れた・回す）: 新しい鍵を SE/HSM で → 管理者が一覧に足す → 新しい鍵で全部出し直す → 旧い鍵を一覧から外す。順は 5.2b の表。
9. **扉の故障。** 扉を替え、新しい記録の公開鍵を台帳へ。古い記録は伝票と照らす。
10. **発行者の機械の故障。** 予備にイメージを入れ、控えから台帳を戻す。同日中（R-AP-24）。その間、扉は最後の一覧で動く。復元の訓練を年に一度（K-08）。
11. **漏れた時の順。** K-15: 止める → 範囲を記録で知る → 作り直す → 知らせる → 書く。

## 6. Wallet の口（形だけ空ける。条件は未読）

- R-AC-18: Wallet（Apple、Google）の鍵は**発行者の一つ**として扱い、発行と失効は台帳から。Wallet の会社が止まっても、カードや暗証番号で開く。
- Apple の Access Program の形（Platform Security の資料）: パートナーのサーバーは Apple と mTLS か JWT、利用者はパートナーごとに匿名化された識別子で iCloud の口座に結ぶ、端末の数の上限はパートナーが決める、資格情報は Apple の HSM で包み直され Apple の外で平文にならない。
- この設計での当て方: 発行者の機械に「Wallet への配布」という経路を一つ足す。台帳の主体 ↔ Apple の匿名の識別子の対応を台帳が持つ。失効は台帳から Apple へ。**パートナー側の保存・審査・機械の条件は契約を結ぶまで分からない**ので、ここは空欄。
- Aliro（家の鍵の開かれた規格、1.0 は 2026-02 公開）は層 1 の規格で、層 2 からは「資格情報の形が Aliro の物」になるだけ。読取機を自分で作るならこちらが先（halo のデータベース §5 の順）。

## 7. 顧客ごとの分離（業者としてやる時）

R-AC-09: 顧客ごとに別の発行者の鍵。一つが漏れても他の顧客に届かない。事実で決まる形:
- 顧客が数件で SE/HSM の鍵の枠が足りるなら、一台の発行者の機械に顧客ごとの鍵と台帳（別のファイル、別の role）。
- 枠が足りない、または顧客が「自分の機械で」を求める（R-AC-19）なら、顧客ごとに発行者の機械（miniPC 一台ずつ）。売る側は顧客の管理者を育てる（R-RS-17）。
- どちらでも、記録は顧客ごとに別の連鎖。

## 9. 決めること（それぞれ、何の事実で決まるか）

1. **台帳を SQLite にするか PostgreSQL にするか。** 事実: 主体と扉の数、同時に書く人の数（一人なら SQLite で足りる）、R-AC-13（halo の PostgreSQL と同じ機械に置かない）。
2. **失効の配り方。** 事実: 扉に網が届く時間の割合。常に届くなら押す（push）、届かない時間が長いなら扉が取りに来る（pull）＋ R-AC-14 の最長の時間を短く。
3. **管理の画面をどこで動かすか。** 事実: 管理者の PC で動く Flet のアプリ（発行者の機械へ WireGuard）か、発行者の機械の上の Web（口が一つ増える。K-07）か。
4. **Wallet の経路を最初から入れるか。** 事実: Apple の条件（未読）と費用（Developer Program 99 USD/年、Access Program は契約）。最初はカードとアプリで動かし、Wallet は発行者の一つとして後から足せる形（R-AC-18）。
5. **二人の「もう一人」**（鍵の管理の仕組み §6 の 1 と同じ）。
