# halo の 11434・11435 に token を掛ける（手順）

`docs/鍵の管理の仕組み.md` §5 の歩 3（K-07 口を最小に）。決まりは同じ文書の K-01（一つの鍵に一つの役）、K-03（置き場）、K-13（AI は鍵を見ない）、K-14（在庫表）、K-15（漏れた時の順）。halo の事実は `docs/halo のデータベース.md` §0・§1（Debian 13、口 22・8080・11434・11435、11434・11435 は認証無し、IPv6 のグローバルアドレスあり、外から届くかは未確認）。

書いた日: 2026-11-06（Opus。halo には繋がずに書いた。作者が halo で順に打つ）。この repo を書いた機械には caddy が無く、`caddy validate` はまだ走らせていない。c の validate が最初の確かめ。

## 0. 形

```
LAN の機械 ──→ halo :11444（Caddy）── Bearer が一致 ──→ 127.0.0.1:11434（Glimmer、llama-server）
           ──→ halo :11445（Caddy）── Bearer が一致 ──→ 127.0.0.1:11435（sd-server）
                         └ 一致しない・無い → 401
外（IPv4 も IPv6 も）──→ ufw で 22・11444・11445 も LAN の外からは閉じる。11434・11435 は機械の外から届かない
```

- 外向きの口の番号は元の口に 10 を足した物（11444・11445）にした。元の番号を外に残すには、Caddy を LAN の IP だけに縛る必要があり、その IP を設定に書く事になる。番号を変える方が設定に IP が出ず、元のサービスを `127.0.0.1` に縛るだけで済む。代わりに、呼ぶ側の URL の口の番号が変わる（末尾の「使う側」）。
- token は口ごとに一つ（K-01）。Glimmer の token では絵の口に入れず、逆も同じ。
- token の値は Caddyfile にも repo にも書かない。halo の `/etc/caddy/halo.env`（root:root 600）に作者が書き、systemd が Caddy に環境変数で渡す（形 A）。盤の上で暗号化したいなら systemd の credential（形 B）。
- この手順のどこでも、token の値を Claude の会話、repo、画面の録画に出さない（K-13）。値を見るのは作者の端末だけ。

置く物（この repo の `deploy/halo/`）:

| ファイル | halo の置き場 |
|---|---|
| `Caddyfile` | `/etc/caddy/Caddyfile` |
| `caddy.service.d/override.conf`（形 A） | `/etc/systemd/system/caddy.service.d/override.conf` |
| `caddy.service.d/credential.conf.example`（形 B、A の代わり） | 同じ場所に `override.conf` として |
| `halo.env.example` | 見本だけ。本物は a で作る `/etc/caddy/halo.env` |
| `ports.toml` | 置かない。作者の機械で kagi が読む（e） |
| `inventory.example.toml` | 置かない。作者の在庫表に写す（f） |

halo へ写すのは作者の手で（`scp deploy/halo/Caddyfile deploy/halo/caddy.service.d/override.conf halo:` の類）。

## a. token を二つ作り、`/etc/caddy/halo.env` に入れる

値を画面にも引数にも出さずに作って書く。`printf` は shell の組み込みなので、値は `ps` に出ない。

```sh
sudo install -d -m 755 /etc/caddy
sudo bash -c 'umask 077
  g=$(head -c 32 /dev/urandom | base64 | tr "+/" "-_" | tr -d "=")
  s=$(head -c 32 /dev/urandom | base64 | tr "+/" "-_" | tr -d "=")
  printf "HALO_GLIMMER_TOKEN=%s\nHALO_SD_TOKEN=%s\n" "$g" "$s" > /etc/caddy/halo.env'
sudo chown root:root /etc/caddy/halo.env
sudo chmod 600 /etc/caddy/halo.env
sudo ls -l /etc/caddy/halo.env          # -rw------- root root
sudo grep -c '=.\+' /etc/caddy/halo.env  # 2（二行とも値がある。値は出さない）
```

- 32 バイトの乱数を URL でも安全な base64 にした物（43 字）。
- 呼ぶ側へ渡すのは作者が自分の端末で（`sudo grep HALO_SD_TOKEN /etc/caddy/halo.env` を見て、呼ぶ機械の設定ファイル（600）に書く）。会話や chat には貼らない。

**形 B（systemd の credential）にするなら**、a の代わりに:

```sh
systemd-creds has-tpm2        # TPM があるか（K-03。無くても動くが、機械の鍵に結ばれる）
sudo install -d -m 700 /etc/credstore.encrypted
for n in halo-glimmer-token halo-sd-token; do
  sudo bash -c "head -c 32 /dev/urandom | base64 | tr '+/' '-_' | tr -d '=\n' \
    | systemd-creds encrypt --name=$n - /etc/credstore.encrypted/$n"
done
sudo ls -l /etc/credstore.encrypted
# 呼ぶ側に渡す時だけ、作者の端末で: sudo systemd-creds decrypt /etc/credstore.encrypted/halo-sd-token -
```

## c. Caddy を入れ、Caddyfile を置き、起動する

```sh
sudo apt install caddy
caddy version                            # 版を控える（Caddyfile は 2.6 からある書き方だけを使った。Claude の記憶）
```

Debian の caddy は入れた時点で既定の Caddyfile（:80）で動き出す。下で置き換える。

```sh
sudo cp ~/Caddyfile /etc/caddy/Caddyfile
sudo install -d /etc/systemd/system/caddy.service.d
sudo cp ~/override.conf /etc/systemd/system/caddy.service.d/override.conf   # 形 B なら credential.conf.example をこの名で
sudo caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile        # "Valid configuration" が出るまで先へ進まない
sudo systemctl daemon-reload
systemctl cat caddy | grep -E 'ExecStart|EnvironmentFile|LoadCredential'     # override が効いている。--environ が無い
sudo systemctl restart caddy
systemctl status caddy --no-pager
sudo ss -ltnp | grep caddy               # *:11444 と *:11445 だけ（:80 も :2019 も無い）
```

- 元の `caddy.service` の `ExecStart` は `caddy run --environ …` で、`--environ` は起動の時に環境変数を全部 journal に出す。override.conf はこれを外している。外れているかを上の `systemctl cat` で必ず見る（K-03）。
- Caddyfile は `admin off`（管理の口 2019 を開けない）。設定や token を変えた時は `reload` でなく `sudo systemctl restart caddy`。
- validate が通らない時: 一番疑わしいのは `expression` の行（placeholder と文字列の足し算）と `log` の `format filter`。エラーの行番号を見て https://caddyserver.com/docs/caddyfile/matchers#expression と https://caddyserver.com/docs/caddyfile/directives/log#filter の今の書き方に合わせる。

token が journal と記録に出ていない事を見る（K-03。値は画面に出さず、数だけ）:

```sh
sudo bash -c 'journalctl -u caddy --no-pager | grep -c -F -f <(sed -n "s/^HALO_[A-Z]*_TOKEN=//p" /etc/caddy/halo.env)'   # 0
sudo bash -c 'cat /var/log/caddy/halo-*.json 2>/dev/null | grep -c -F -f <(sed -n "s/^HALO_[A-Z]*_TOKEN=//p" /etc/caddy/halo.env)'  # 0（e の後にもう一度）
```

## d. ufw で外向きの口を 22・11444・11445 だけにし、LAN の外から閉じる

今の形を先に控える（11-04 に 11434・11435 を LAN に開けた規則があるはず）。

```sh
sudo ufw status verbose
sudo ufw status numbered
grep '^IPV6=' /etc/default/ufw           # IPV6=yes（IPv6 にも同じ既定が掛かる）
```

`<LAN の範囲>` は作者の家の IPv4 の範囲（ネットワーク/長さ の形）。ssh で halo に入って作業しているなら、22 の規則を enable より先に入れる（締め出されない）。

```sh
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow from <LAN の範囲> to any port 22 proto tcp
sudo ufw allow from <LAN の範囲> to any port 11444 proto tcp
sudo ufw allow from <LAN の範囲> to any port 11445 proto tcp
sudo ufw status numbered                 # 11434・11435・8080 を開けている規則の番号を見て
sudo ufw delete <番号>                   # 一つずつ消す（消すと番号が詰まるので、毎回 status numbered を見直す）
sudo ufw enable
sudo ufw status verbose
```

- IPv4 の `from <LAN の範囲>` の規則は IPv6 には当たらない。IPv6 は既定の deny incoming だけが当たるので、22・11444・11445 も IPv6 からは閉じる。家の中で IPv6 で halo に入る機械があるなら、IPv6 の LAN の範囲（`ip -6 addr` で見る。グローバルの範囲は入れない）を同じ形で足す。
- 8080 は何か未確認のまま。閉じた後に困る物（Glimmer の画面など）が出たら、要るかを決めて、要るなら 127.0.0.1 に縛って門をもう一つ足す（`ports.toml` の末尾）。
- Caddy は全部の IP の 11444・11445 で聞いている（`*`）。LAN の外から届かないのは ufw だけが理由になる。ufw を止めた日は門だけが残る（token は効く）。

## e. 確かめる

**LAN の別の機械から**（`<halo>` は halo の名か LAN の IP。作者の端末で打つ）:

```sh
curl -i http://<halo>:11444/v1/models                       # 401、WWW-Authenticate: Bearer realm="halo-glimmer"
curl -i -H 'Authorization: Bearer wrong' http://<halo>:11445/v1/models   # 401
curl -i -m 5 http://<halo>:11434/v1/models                  # 繋がらない（ufw と 127.0.0.1 の両方で閉じている）
curl -i -m 5 http://<halo>:11435/v1/models                  # 繋がらない

# 本物の token で。値を引数に出さないよう、read で読み、-H @- で標準入力から渡す
read -rs T                                                    # halo.env の HALO_SD_TOKEN の値を貼る（画面に出ない）
printf 'Authorization: Bearer %s\n' "$T" | curl -i -H @- http://<halo>:11445/v1/models     # 200
printf 'Authorization: Bearer %s\n' "$T" | curl -i -H @- http://<halo>:11444/v1/models     # 401（口ごとに別の token。K-01）
unset T
# Glimmer の token でも同じ形で :11444 が 200、:11445 が 401
```

**LAN の外から**（スマートフォンの回線など、家の網の外の機械で。halo の IPv4 の外の口と IPv6 のグローバルアドレスの両方）: 22・8080・11434・11435・11444・11445 のどれにも繋がらない事（`curl -m 5`、`nc -vz -w 5`）。届いたら d に戻る。これで `docs/halo のデータベース.md` §0 の「外から届くかは未確認」が埋まる。

**口の表と突き合わせる**（K-07）:

```sh
# halo で
sudo ss -ltnp > ss-halo.txt              # sudo で、他の利用者のプロセスの名前も出る
# 作者の機械（seed の repo）に写して
kagi check ports --dir deploy/halo --host halo --ss ss-halo.txt
# 「表と口の一覧に差は無い。」なら終わり。差が出たら表の通りに直すか、確かめた上で ports.toml に足す
```

`ss-halo.txt` は LAN の IP を含みうるので、repo には入れない。

**記録に token が出ていない**: c の末尾の二つ目の行を、e の curl の後にもう一度走らせて 0。記録の行には `status`（200 か 401）、`request.remote_ip`、`request.uri` が残る。この記録を別の機械へ送るのは作者（K-06。`/var/log/caddy/halo-glimmer.json`、`halo-sd.json`）。

## g. 漏れた時（K-15）

漏れた方だけを作り直す（K-01。もう一つの口は止めない）。例は絵の口:

```sh
# 1. 止める: 新しい値に書き換えて restart。古い値はこの時に効かなくなる
sudo bash -c 'umask 077; f=/etc/caddy/halo.env
  n=$(head -c 32 /dev/urandom | base64 | tr "+/" "-_" | tr -d "=")
  { grep -v "^HALO_SD_TOKEN=" "$f"; printf "HALO_SD_TOKEN=%s\n" "$n"; } > "$f.new"
  chown root:root "$f.new"; chmod 600 "$f.new"; mv "$f.new" "$f"'
sudo systemctl restart caddy
# 形 B なら: /etc/credstore.encrypted/halo-sd-token を a の形 B の行で作り直して restart

# 2. 古い値が効かない事を LAN の機械で（e の形で、古い値で 401）
# 3. 範囲を知る: 漏れた後に通った要求（status 200）の時刻と相手
sudo grep '"status":200' /var/log/caddy/halo-sd.json | tail     # jq があれば jq -c 'select(.status==200)|{ts,ip:.request.remote_ip,uri:.request.uri}'
# 4. 作り直す: 呼ぶ側の設定を新しい値に。在庫表の made と expires を書き直す
# 5. 知らせる・書く: kagi log add で一行、何が起きたかを作者の言葉で
```

Glimmer の口なら `HALO_SD_TOKEN` を `HALO_GLIMMER_TOKEN` に、記録を `halo-glimmer.json` に読み替える。両方漏れたら両方を同じ順で。

## TLS について（今は掛けていない）

門は素の HTTP で、token は LAN の中を平文で流れる。家の LAN（無線を含む）に入れる人には見える。家の中だけで使う間はこれを受け入れ、**11444・11445 を家の外へ開けない**（d）。家の外から使う日は、この口を開けるのでなく、`docs/halo のデータベース.md` §2・§3 の形（deb2 が入口、halo とは WireGuard）にする。LAN の中でも暗号化したくなったら、Caddyfile の site を名前付き（例 `halo.lan:11444`）にして `tls internal` を足し、呼ぶ側に Caddy の内部の CA を信頼させる（Caddy の説明書の `tls` の項）。

もう一つ: token の照合は CEL の `==` で、時間が一定の比較ではない。32 バイトの乱数で、LAN の中だけなので、Claude はこれで足りると読む（作者が確定）。
